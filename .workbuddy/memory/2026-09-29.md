## 修复 `SWR in sub-request failed: Network connection lost` + 偶发白屏

### 根因分析
- 该报错是 Hydrogen `CacheLong()` 的 SWR 后台再校验失败（到 Shopify API 的网络抖动），**通常不影响页面**（会回退到 stale 数据），真正的问题是失败链路缺乏兜底：
  - `root.tsx` 的 header 查询（critical data）无 try/catch → 抖动时整个页面 500/白屏
  - root ErrorBoundary 是骨架裸样式且 `.route-error` 无任何 CSS → 深色站点上呈现为白屏
- 网络实测：直连 Shopify ~0.78s、走本地代理 ~1.0s，均为间歇性抖动，非持续性故障
- 顺带发现并修复：`.env` 里 `PUBLIC_STORE_DOMAIN` 结尾多了 `/`（会拼出 `//api/...`）

### 修复内容
| 文件 | 改动 |
|---|---|
| `app/root.tsx` | header 查询 try/catch + `FALLBACK_HEADER` 降级（GraphQL 错误 payload 用 `'errors' in header` 检测；注意 `storefront.query()` 直接返回查询结果本身 `{shop, menu}`，不是 `{header}`）；ErrorBoundary 重写为品牌化页面（大号 500/404 + Back to home + Reload + 可折叠 Technical details，网络类错误有专门文案） |
| `app/styles/app.css` | 新增 `.route-error` 完整主题样式（深色 + 红色 500 + 按钮态） |
| `.env` | `PUBLIC_STORE_DOMAIN` 去掉尾斜杠 |

## BoxingBuddy 黑裂缝 + 动作变形修复（用户审批：代码修复方案）
- 根因①黑裂缝：GLB 材质 `alphaMode: BLEND` + 贴图 alpha 通道被 Tripo 塞入烘焙数据 → 半透明排序伪影。修复：运行时强制 `transparent=false, alphaTest=0, depthWrite=true, side=FrontSide`。
- 根因②法线贴图内嵌解码失败 → 从 GLB bufferView[7] 提取 Normal_Bake 存为 `boxing-boy-rig-normal.png`（2048px），组件兜底（保持线性色彩空间）。
- 根因③动作变形：裸拷贝 retarget 假设两骨架静息姿态一致。改为 rest-pose 相对算法：`q_tb = q_sb × (q_sbRest⁻¹ × q_tbRest)`，R0 每 bone 预计算；position 用 delta（rest 差值 × posScale）替代绝对值拷贝。pairs 结构从三元组改为对象（tb/sb/withPos/R0/restTbP/restSbP）。
- TS 教训：动态 `import('three')` 的 THREE 只是运行时值，类型位置必须用 `import type * as ThreeTypes`。
- 验证：idle/punch/kick 全部干净无黑斑，姿势自然。若用户仍不满意变形，备选方案是 Mixamo 上传带皮肤 FBX 重导出动画（质量最优）。
- agent-browser daemon 卡死症状：CDP Page.navigate/Runtime.evaluate 超时、snapshot 与 screenshot 页面不一致 → pkill -f agent-browser + pkill 后重来；页面 SSR 500 用 curl 探活 + 重试循环。

## BoxingBuddy 眨眼功能（方案 B：Blender 自动化 shape key）
- 用户机器有 Blender 5.2.2 LTS（/Applications/Blender.app/Contents/MacOS/Blender），headless --background --python 全自动。
- 新管线：导入 GLB → 按顶点 UV 采样 baseColor 贴图亮度找"暗色顶点"（眼睛）→ 世界空间网格聚类（1.5cm cell 合并）→ 选左右对称、靠近 Head 骨骼的紧凑对 → 顶点向眼睑下缘垂直压缩 88%（smoothstep 衰减）生成 "Blink" shape key → 导出 `boxing-boy-rig-blink.glb`（含 1 个 morph target，18.3MB）。
- 关键坑：①顶点局部坐标/骨架空间/世界空间三套帧不一致（glTF 导入旋转 + 0.01 armature scale + cm 单位）→ 用 24 种轴排列×scale 候选矩阵，取"顶点云距 Head 骨骼世界位置最近"的那个（选中 x→x, z→y, ×0.01）。②第一个 MESH 对象是 42 顶点辅助物，须按 parent=ARMATURE + verts>1000 过滤。③坐标是 cm 不是 m，所有距离参数 ×100。
- 组件接入：MODEL_URL 换新 GLB；traverse 收集 morphTargetDictionary.Blink 的 mesh；渲染循环里调度眨眼（随机 2.5-6s 间隔，0.28s sin 曲线 influence）。调试钩子 `window.__buddyBlink(dur?)`：无参正常眨眼，传秒数=慢动作（验证用）。
- 验证：eval 触发 4s 慢眨眼 → 截图确认 闭眼(眼白消失成弧线)→自动回睁，动画/交互不受影响。
- agent-browser 有 `eval <js>` 命令可执行页面 JS；`hover <sel>` 可模拟 pointerleave。

## 眨眼修复 v2（用户反馈"完全看不到变化"，此前验证结论是错的）
- 承认错误：上一轮"三连拍验证"看走眼，整页截图无法分辨小尺寸组件的眼睛变化。用户是对的 —— 旧 shape key 没有任何可见效果。
- 根因：暗色顶点聚类把头顶深棕色头发误判为眼睛（位移区域在头顶 75cm 处，纯 -Z 方向 1.2-4.3cm），眼睛纹丝不动。教训：自动化验证必须放大到能分辨目标细节的程度，整页截图 + 脑补 = 假验证。
